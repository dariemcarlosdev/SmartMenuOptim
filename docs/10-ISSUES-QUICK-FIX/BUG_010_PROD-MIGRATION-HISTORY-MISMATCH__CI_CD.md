## Summary

The `apply-prod-migrations` CI job failed every time it ran against the Neon production
PostgreSQL database.  EF Core tried to `CREATE TABLE "AdminUsers"` (the first operation
in migration `20251103163754_FixPostgreSQLIndexSyntax`) but that table already existed in
the production database, causing Postgres to reject the command with error code `42P07`.

> **Note**: The `verify-database-migrations` job (which spins up a *fresh* ephemeral
> Postgres container) continued to pass — the problem was **only** on the persistent
> production Neon database.

## Root Cause

### Background — What Happened to the Production Database

The production Neon database was originally provisioned by an older set of migrations
(or by the application's `DbSeeder.ConnectToDatabaseAsync()` calling
`context.Database.MigrateAsync()` on startup).  At some point the old migration files
were **squashed / renamed** into a single "initial" migration:

```
20251103163754_FixPostgreSQLIndexSyntax   ← new "first" migration (combines old ones)
20251104020608_UpdateProfileRelationshipsAndIndexes
20251104145033_FixAdminUserIdentityGeneration
... (subsequent migrations)
```

The Neon database retained the schema from the old migrations but its
`__EFMigrationsHistory` table either:

* contained the **old** migration IDs (which no longer exist in the project), or
* was empty (database was bootstrapped outside of EF tracking).

Either way, `20251103163754_FixPostgreSQLIndexSyntax` was **not** present in the history
table.

### Why `dotnet ef database update` Fails

```
┌──────────────────────────────────────────────────────────┐
│  __EFMigrationsHistory on Neon DB                        │
│  ─────────────────────────────────────────────────────── │
│  ❌  20251103163754_FixPostgreSQLIndexSyntax  (missing)  │
│  ❌  20251104020608_UpdateProfileRelations…   (missing)  │
│  ...                                                     │
└──────────────────────────────────────────────────────────┘

EF Core sees the migration is not recorded → tries to run its Up() method
→ Up() calls CREATE TABLE "AdminUsers" → table already exists → 42P07 error
```

EF Core's `database update` command is **idempotent only with respect to its own
history table**.  It does not check whether a table already exists in the database;
it blindly executes every `CREATE TABLE` that belongs to a pending migration.

### Why `DesignTimeDbContextFactory` Doesn't Prevent the Issue

The factory in `SmartMenuOptim.Infrastructure` is declared `internal`, so EF Core tooling
cannot discover it from the startup project.  EF falls back to running `Program.cs` to
extract the `DbContext` from the DI container.  While doing so it prints:

```
Loading configuration from User Secrets and Environment Variables (Development mode)
```

The `InitializeDataBaseAsync()` call is made *after* `app.Build()` and *before*
`app.Run()`.  EF intercepts the host *before* that code runs, so the Seeder's own
`MigrateAsync()` does **not** execute during design-time context discovery — leaving
the Neon history table untouched.

## Fix Applied

**File changed**: `.github/workflows/ci-cd.yml`

The `apply-prod-migrations` step was rewritten from a single `dotnet ef database update`
call into a three-phase idempotent script:

### Phase 1 — Generate an idempotent EF Core migration script

```bash
dotnet ef migrations script --idempotent \
  --output /tmp/migration_idempotent.sql \
  --project SmartMenuOptim.API/SmartMenuOptim.API.csproj
```

`--idempotent` wraps every migration block in a guard:

```sql
DO $EF$
BEGIN
IF NOT EXISTS(
    SELECT 1 FROM "__EFMigrationsHistory"
    WHERE "MigrationId" = '20251103163754_FixPostgreSQLIndexSyntax'
) THEN
    CREATE TABLE "AdminUsers" ( ... );
    ...
    INSERT INTO "__EFMigrationsHistory" ...;
END IF;
END $EF$;
```

This skips migrations that are **already recorded** in history.

### Phase 2 — Add `IF NOT EXISTS` to all DDL statements

Even with `--idempotent`, if a migration is **not** in history but its tables already
exist (our exact scenario), Postgres will still throw `42P07` inside the DO block.
A `sed` post-processing step promotes all DDL to their idempotent forms:

```bash
sed -E \
  -e 's/CREATE TABLE "([^"]+)"/CREATE TABLE IF NOT EXISTS "\1"/g' \
  -e 's/CREATE INDEX "([^"]+)"/CREATE INDEX IF NOT EXISTS "\1"/g' \
  -e 's/CREATE UNIQUE INDEX "([^"]+)"/CREATE UNIQUE INDEX IF NOT EXISTS "\1"/g' \
  /tmp/migration_idempotent.sql > /tmp/migration_final.sql
```

The combined effect:

| Scenario | Behaviour after fix |
|---|---|
| Migration in history, tables exist | DO block skipped entirely (history guard) |
| Migration **not** in history, tables exist | DO block runs; DDL silently skips existing objects; `INSERT INTO __EFMigrationsHistory` commits the record ✅ |
| Migration not in history, tables **don't** exist | DO block runs; DDL creates objects; history updated ✅ |
| Subsequent migrations (ALTER TABLE etc.) | History guard skips already-applied ones; new ones apply normally ✅ |

### Phase 3 — Apply via `psql`

The final script is executed directly against Neon using `psql`, supporting both the
`postgresql://` URI format (Neon's default) and the Npgsql semicolon key=value format:

```bash
CONN="${NEON_CONN_STRING}"
if [[ "$CONN" == postgresql://* || "$CONN" == postgres://* ]]; then
  psql "$CONN" -v ON_ERROR_STOP=1 -f /tmp/migration_final.sql
else
  # parse Npgsql key=value pairs into PSQL env vars
  PGHOST=...  PGDATABASE=...  PGUSER=...  PGPASSWORD=...  PGSSLMODE=...
  psql -h "$PGHOST" ... -v ON_ERROR_STOP=1 -f /tmp/migration_final.sql
fi
```

`ON_ERROR_STOP=1` ensures any genuine (non-idempotency) error still fails the job.

### Before / After — Workflow Step

**Before (broken):**
```yaml
- name: Apply EF Core Migrations to Azure PostgreSQL
  env:
    ConnectionStrings__DefaultConnection: ${{ secrets.NEON_POSTGRES_CONNECTION_STRING }}
  run: dotnet ef database update --project SmartMenuOptim.API/SmartMenuOptim.API.csproj
```

**After (fixed):**
```yaml
- name: Apply EF Core Migrations to Azure PostgreSQL
  env:
    ConnectionStrings__DefaultConnection: ${{ secrets.NEON_POSTGRES_CONNECTION_STRING }}
    NEON_CONN_STRING: ${{ secrets.NEON_POSTGRES_CONNECTION_STRING }}
  run: |
    sudo apt-get install -y -q postgresql-client
    dotnet ef migrations script --idempotent \
      --output /tmp/migration_idempotent.sql \
      --project SmartMenuOptim.API/SmartMenuOptim.API.csproj
    sed -E \
      -e 's/CREATE TABLE "([^"]+)"/CREATE TABLE IF NOT EXISTS "\1"/g' \
      -e 's/CREATE INDEX "([^"]+)"/CREATE INDEX IF NOT EXISTS "\1"/g' \
      -e 's/CREATE UNIQUE INDEX "([^"]+)"/CREATE UNIQUE INDEX IF NOT EXISTS "\1"/g' \
      /tmp/migration_idempotent.sql > /tmp/migration_final.sql
    CONN="${NEON_CONN_STRING}"
    if [[ "$CONN" == postgresql://* || "$CONN" == postgres://* ]]; then
      psql "$CONN" -v ON_ERROR_STOP=1 -f /tmp/migration_final.sql
    else
      PGHOST=$(echo "$CONN" | grep -oiP '(?<=Host=)[^;]+')
      PGPORT=$(echo "$CONN" | grep -oiP '(?<=Port=)[^;]+' || echo "5432")
      PGDATABASE=$(echo "$CONN" | grep -oiP '(?<=Database=)[^;]+')
      PGUSER=$(echo "$CONN" | grep -oiP '(?<=Username=)[^;]+')
      export PGPASSWORD=$(echo "$CONN" | grep -oiP '(?<=Password=)[^;]+')
      PGSSLMODE=$(echo "$CONN" | grep -oiP 'ssl ?mode=[^;]+' | sed -E 's/.*=//' \
                  | tr '[:upper:]' '[:lower:]')
      export PGSSLMODE=${PGSSLMODE:-require}
      psql -h "$PGHOST" -p "$PGPORT" -d "$PGDATABASE" -U "$PGUSER" \
        -v ON_ERROR_STOP=1 -f /tmp/migration_final.sql
    fi
```

## Follow-up Fix — `psql: error: invalid sslmode value: ""` (2026-07-26)

**Symptom:** `apply-prod-migrations` reached the `else` (Npgsql key=value) branch and failed with:

```
psql: error: invalid sslmode value: ""
Error: Process completed with exit code 2.
```

**Root cause:** the `PGSSLMODE` line piped `grep` into `tr`, then appended `|| echo "require"`.
A shell pipeline's exit status is that of its **last** command (`tr`), which returns `0`
even on empty input — so the `|| echo "require"` fallback **never fired** when the
connection string had no `SSL Mode=` key. `PGSSLMODE` was exported as `""`, and psql
rejects an empty sslmode.

**Fix:** assign first, then default with parameter expansion `${PGSSLMODE:-require}`
(fires on empty **or** unset). Also relaxed the match to `ssl ?mode=` so both
`SSL Mode=` and `SslMode=` (both valid Npgsql spellings) are recognized.

## Prevention / Long-term Recommendations

| Recommendation | Rationale |
|---|---|
| **Never delete applied migrations** from a project without a matching squash migration and a one-time `__EFMigrationsHistory` repair script | Squashing without history repair is the root cause of this class of issue |
| **Make `DesignTimeDbContextFactory` public** (or move it to the API project) | Prevents EF tooling from falling back to running `Program.cs`, which is slower and fragile |
| **Use `dotnet ef migrations script --idempotent` as the standard prod migration strategy** | More resilient than `database update` against drift between schema and history |
| **Add a migration history validation step** to `verify-database-migrations` | Catch drift before it reaches production |
